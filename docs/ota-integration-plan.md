# OTA 管理助手：调研与实施方案

> 本文保留初始调研结论及当时的验证范围。项目现已实现 Python SDK、CLI 和 HTTP API，当前使用与执行规则见 [README](../README.md)。

调研日期：2026-11-17（北京时间）

目标系统：https://nota.urovo.com:7003/UpdateConsole/login.jsp

## 1. 结论

推荐使用“直接调用现有后台接口 + 自动登录和会话管理”的方式实现，无须依赖浏览器逐次点击。已完成证书连接、账号登录、OTA 列表查询和一条任务的 SN 规则读取。

当前发现的是网页自身使用的 `.action` 接口，并非已确认的官方开放 API。证书用于 TLS 层认证，账号密码用于应用层登录，二者不能相互替代。没有发现可免登录使用的业务接口。

本轮仅做登录及只读调研。未上传升级包，未新增或删除任务，未修改 SN，未启停任务，也未发起推送。写操作接口的信息来自页面表单和 JavaScript，尚未进行写入验证。

## 3. 接口映射

以下路径统一位于 `https://nota.urovo.com:7003/UpdateConsole/` 下。所有业务调用按需携带客户端证书及已登录会话。

| 能力 | 方法与路径 | 关键参数 | 验证程度 |
| --- | --- | --- | --- |
| 获取登录页 | GET `login.jsp` | 无 | 已调用 |
| 登录 | POST `Login.action` | `userId`、`password`；跟随登录页实际 form action | 已调用成功 |
| OS 管理页 | GET `versionManage_goVersionPage.action` | 无 | 已调用 |
| 查询 OTA | POST `versionManage_queryPgmList.action` | `currPage`、`pageSize`、`osPgmVersion.*` 筛选字段 | 已调用成功 |
| 新建表单 | GET `versionManage_selectDevType.action` | 无 | 已读取 |
| 配置候选值 | POST `versionManage_aotoComplete.action` | 页面未传额外字段 | 仅确认页面调用，尚未调用 |
| 新增 OTA | POST `versionManage_addPgm.action` | multipart：升级包、版本及设备配置等 | 已定位，未执行 |
| 删除 OTA | POST `versionManage_batchDeletePgm.action` | 重复的 `Id` 字段，可表达多选 | 已定位，未执行 |
| 读取 SN | GET `versionManage_findRegulation.action` | `regulationOsId` | 已调用成功，返回 HTML |
| 保存 SN | POST `versionManage_addReg.action` | `regulationOsId`、`dvcFlagReg`、`regularContent`，以及原表单字段 | 已定位，未执行；页面使用 multipart 表单 |
| 启用/禁用 | POST `versionManage_changeOsStatus.action` | `osId`、`status`、`osVersion`、`jPushFlag` | 已定位，未执行 |

### 查询兼容细节

- 筛选字段包括 `osPgmVersion.osType`、`devType`、`model`、`standard`、`osVersion`、`osLanguage`、`bagType`、`highVersion`、`status`、`remarks`、`startTime`、`endTime`；后面这些字段同样带 `osPgmVersion.` 前缀。
- 分页字段实际为 `currPage` 和 `pageSize`，不是常见的 `page` / `pagesize`。
- 首次只传分页参数返回 HTTP 500；按页面发送全部筛选键、允许值为空后返回正常 JSON。实现应复现页面参数结构。
- 列表主要字段包括 `id`、`osVersion`、`devType`、`model`、`standard`、`effective`、`bagType`、`highVersion`、`period`、`remarks`、`updDate` 等。
- 页面以 `effective=1` 表示生效、其他值表示禁用；`status` 在列表中用于显示规则信息，不应当作任务启停字段。

### 固件 ZIP 识别能力补充验证

2026-11-17 根据用户截图，以设备 `SQ27M`、版本 `13.24.0826.01` 做只读筛选，返回一条记录：ID `24295`、Android、硬件 `DS`、定制 `PKG-XX`、完整更新包。

- 该记录的 `pathFileName`、`path`、`md5Value` 均为 `null`。
- `fileSize=992199`，当前未核实该字段单位，不进行字节或 MB 换算。
- `ossExistsFlag=0`，其语义尚未核实，不能据此断言 ZIP 丢失或不可下载。
- API 返回语言为“英文”，截图显示“中文”，因此不能将其无条件视为截图记录的完全一致快照。

结论：已验证列表接口可以定位 OTA 配置，但不能保证识别每条任务的实际 ZIP 文件名或内容。字段存在不代表包含有效值；不得用版本号猜测 ZIP 文件名。后续需找到并验证平台实际提供的包详情、下载或上传记录入口，或由平台方提供相关接口。若获得授权下载，再通过 ZIP 元数据、包内清单及内容摘要验证实际固件；当前未下载固件。

后续根据用户提供的设备接口 `https://nota.urovo.com:7000/Update/osUpdate` 已成功拿到固件 JSON：对任务 `23159`，使用其 SN 规则中的一个 SN 作为 `dvcId`、`devType=K388Pro_WE_StandardOS-N`、`osLanguage=english`、当前版本 `14.26.0508.02`，返回目标版本 `14.26.0827.01`、`updURL`、`size` 及 `md5Value`。最初沿用示例的 `dvcId=9bd849e1` 时返回空 `datas`。

设备接口的 `devType` 按本次已验证情况由设备、硬件和定制类型用下划线连接；`osVersion` 是设备当前版本，不是直接填目标版本。必须核对返回版本与 URL 中任务 ID，不能保证任意配置都能通过升级匹配规则获得其自身固件。用户已明确不下载 ZIP 核实内容，当前实现只返回 JSON，不获取 ZIP 内容。

## 4. 四类功能如何实现

### 4.1 查询 OTA

提供设备类型、版本、硬件配置、定制类型、启停状态、包类型、日期及备注筛选。按服务端分页查询，返回任务 ID 和关键配置。详情组合任务字段与 SN 规则。

自然语言筛选只负责生成结构化条件；写操作必须绑定任务 ID。若同一版本对应多条记录，应显示候选的设备类型、硬件配置和定制类型供选择。

### 4.2 新增或删除 OTA

这里的“新增 OTA”对应平台的“新增 OS 镜像”，需要上传真实 ZIP 升级包，并非只创建一条文本任务。

新增所需信息：系统类型、设备类型、硬件配置、定制类型、版本、语言、完整包或增量包、ZIP 文件、升级时间段。增量包还需要基础版本；此外有强制安装、静默、立即更新、更新提醒及备注字段。

实施时先读取平台允许的设备配置，检查包文件与必要字段，计算文件摘要，提交后查询核验任务是否创建。平台对新增任务的默认启停状态、重复版本处理和失败清理规则仍待测试，不能假定默认禁用或可自动回滚。

用户明确限制：**只能删除当前备注字段 `remarks` 包含字面量 `PATRICK` 的 OTA 任务，区分大小写。** 删除前必须按精确任务 ID 重新读取并检查真实备注；备注为空、不匹配、读取失败或任务不明确时拒绝删除。批量删除逐条检查，任一不符合则不提交整个批次。不得通过先改备注添加标记来绕过限制，也不提供强制删除绕过选项。此标记仅限定可删除目标，本轮研究授权不包含实际删除。

符合上述限制且获得后续实际操作授权时，删除操作记录删除前配置与关联 SN 规则，执行后查询核验。删除是否同步移除包文件、是否可恢复尚不清楚；配置快照不等于升级包备份。

### 4.3 给任务增加或减少 SN

页面保存方式是提交整份 `regularContent`，单项之间以分号分隔，区间以连字符表达。由此推断应采用“读取 → 计算新名单 → 提交整份名单 → 重新读取核验”的流程，而不是只把新增 SN 发给接口。具体后端替换语义仍需测试任务确认。

实现需要支持：

- SN 始终作为字符串处理，保留前导零。
- 增加时去重；重复添加作为无需变更处理。
- 减少不存在的 SN 时作为无需变更处理。
- 从 SN 区间中删除单个 SN 时，按需拆成两个区间，不展开成大量单号。
- 写入前重新读取并比较规则摘要；发现其他人已修改时重新计算，避免覆盖其变更。
- 没有服务端版本号或条件更新时，本地锁只能协调本项目请求，无法完全消除外部网页同时修改的竞争；需明确提示冲突并在写后核验。

页面体现的 SN 约束：

- 标准 SN 为 14 位：前 8 位为字母或数字，后 6 位为数字。
- 标准区间起止前缀一致，按闭区间处理。
- 大于 14 位的特殊 SN 不允许设置结束区间；页面输入上限为 23 位。
- 23 位特殊 SN 要求 `Y3AT582` 前缀。
- 当前页面只展示“具有下列 SN 的设备”模式，值为 `dvcFlagReg=1`，初期只支持该模式。
- 页面阻止保存空 SN 名单。删除最后一个 SN 的后端行为未知，实施前需在测试任务确认；初期应提示该边界并允许用户明确选择先禁用任务，不能将空名单解释为全量设备。

### 4.4 Enable / Disable

对外提供“设置为启用/禁用”的目标状态操作，避免把请求建模为盲目翻转。

- 页面发送 `status=1` 启用、`status=0` 禁用。
- 先读取当前 `effective`；已为目标状态时不重复写入。
- 页面在启用前检查是否存在 SN 规则，应在本项目执行层复现该前置条件。
- `jPushFlag` 控制独立的推送行为；默认不附带推送，只有明确要求时才发起推送。
- 禁用任务是否影响已下载或正在执行的设备升级，本轮没有验证；界面不得将禁用描述为撤回已执行升级。

## 5. 推荐项目结构

推荐先完成本地单用户版本，以 Python 为核心，后续需要多人使用时再部署服务。

```text
简单管理界面 / 自然语言入口
            ↓
结构化操作：查询、上传、SN 增减、设置启停
            ↓
执行层：参数校验、变更预览、任务锁、结果核验、审计
            ↓
OTA 客户端：证书、自动登录、Cookie、接口适配、HTML 规则解析
            ↓
现有 UpdateConsole 服务
```

建议组件：Python + FastAPI 提供服务，HTTPX 维护 HTTP 会话，cryptography 读取 P12，HTML 解析器读取规则表单，SQLite 存储操作记录与配置快照。交互界面先做任务列表、任务详情、上传表单及 SN 差异预览，是否引入复杂前端框架可后续决定。

自然语言层只调用固定业务工具，例如：

- `list_ota(filters)`
- `get_ota(task_id)`
- `create_ota(metadata, package)`
- `delete_ota(task_id)`
- `add_sns(task_id, sns)` / `remove_sns(task_id, sns)`
- `set_enabled(task_id, enabled, push=False)`

原始 Cookie、私钥、账号密码不进入自然语言上下文；外部页面、OTA 备注及导入文件内容作为业务数据处理，不作为执行指令。

账号与证书密码放系统钥匙串等本机秘密存储，代码库只记录配置示例。P12 从受控本地路径读取，解密后的私钥尽量仅在内存或受限临时文件存在，结束后清理。正式信任配置使用平台根 CA 或明确管理的证书信任锚，不能长期使用 `verify=False`。

## 6. 执行可靠性

1. **会话失效检测**：识别重定向登录页及 HTTP 200 中的登录 HTML，避免当作业务成功；自动重新登录。
2. **有限重试**：只读查询可以退避重试；新增、删除、保存规则、启停发生超时时先查询结果，不盲目重复提交。
3. **以实际结果为准**：核验 JSON 类型、业务响应及提交后的真实状态。现有上传页面在 readyState=4 时便提示完成，不能复用这一成功判断。
4. **变更预览**：显示任务 ID、设备配置、SN 增减及推送选项；用户已明确下达的具体操作可直接按授权执行，目标不明确时先选择目标。
5. **默认选项**：新建工作流以禁用为目标，需确认平台默认状态及可控方式后实现；不自动设置强制安装、静默、立即更新或推送。
6. **审计与核验**：记录操作者、时间、目标、前后差异和最终结果，凭据及会话信息脱敏。

## 7. 实施步骤与验收

| 阶段 | 工作 | 验收条件 |
| --- | --- | --- |
| A：只读客户端 | 证书载入、登录、分页筛选、任务和规则详情 | 可重复查询；登录过期能恢复；敏感信息不进入日志 |
| B：测试任务写入 | SN 增减与区间处理、启停、独立推送参数 | 在专门测试任务完成增减和状态往返，写后读回一致 |
| C：包管理 | 上传新增、结果识别、重复检测、删除 | 用测试 ZIP 和备注含 `PATRICK` 的测试任务验证；备注不匹配或读取失败时必须拦截删除；验证失败和超时处理 |
| D：使用入口 | 管理界面、自然语言工具、变更预览及审计 | 用户用中文描述操作，能准确匹配任务并返回可核验结果 |

关键测试应覆盖区间中间删除、前导零、重复添加、删除末个 SN、外部并发修改、会话过期，以及写请求超时后结果不明等业务边界。

粗略工作量：只读版本约 0.5–1 个工作日，四类功能可用的本地 MVP 约 3–5 个工作日；这是基于当前调研的估算，前提是有专用测试任务和测试升级包，写接口没有额外未暴露的流程。多人权限、集中部署和生产运维另计。

## 8. 实施前仍需明确

- 测试任务与测试 ZIP：写入验证应限定在这些对象内。
- 删除最后一个 SN 的预期业务行为，以及平台端实际支持方式。
- 新增后的默认启停状态、重复版本和包文件清理规则。
- 首版使用方式：建议先做当前电脑上的单用户工具，再决定是否部署多人网页。

当前已有足够证据选择直接 HTTP 接入路线，不需要先建设浏览器点击机器人；只有接口流程确实无法复现时，再针对该部分引入浏览器兜底。
